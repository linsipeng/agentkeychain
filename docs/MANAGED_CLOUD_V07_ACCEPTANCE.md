## Staging verification boundary

Use a disposable test account and test values, preferably isolated from the existing staging data. Record versions, timestamps, safe error category, HTTP status and property presence rather than credentials, cookie values, raw assertion bodies or plaintext. Never bypass a real passkey or reuse or reset an existing Vault. Confirm the staging target and rollback plan before operating it; production remains separately authorized.

Keep migrations 0024/0025 and Worker cleanup compatibility together. Retained retirement/successor rows are intentionally protected; an older Worker can attempt to delete them during routine cleanup, causing enrollment to fail closed. Before staging these migrations, verify a rollback-compatible Worker or use a fresh, disposable test database. Do not remove retention guards or roll back a live database ad hoc. Deploy the browser-cookie change with its matching static assets and follow [the cookie rollout notes](BROWSER_SESSION_COOKIE_ROLLOUT.md).
